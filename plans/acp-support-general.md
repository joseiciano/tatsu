# First-class JsonModeChat support for all agents

## Outcome

Every ACP-capable agent Tatsu supports — Claude Code, Opencode, Codex —
gets a first-class JsonModeChat tab driven through the existing
chat-runtime architecture, with **no requirement for a global CLI install
and no install-on-demand prompt**. All runtime dependencies ship with the
app, pinned to exact versions and locked via the lockfile. The renderer
keeps the existing `jsonClaude:*` transport surface and `JsonModeChat`
component; the main process gains per-agent runtimes behind the registry,
and session/tab metadata generalizes so the registry routes per session
by agent kind instead of hard-coding Claude.

Claude keeps its existing Agent SDK transport. Despite its name,
`ClaudeAcpRuntime` is not generic ACP stdio. OpenCode, Codex, and future
ACP-compatible agents share a generic ACP stdio runtime.

"First-class" means a user can, from a chat tab alone: log in, send
prompts, approve or reject tool calls, pick a model, and continue the
conversation after switching the tab between terminal and chat. Phases
1–4 below deliver prompts and streaming only; Phases 5–7 deliver the rest.

## Packaging findings

### electron-builder drops non-hoisted optional platform packages

electron-builder 26.8.1's pnpm collector
(`app-builder-lib/out/node-module-collector/pnpmNodeModulesCollector.js`)
checks each package's `optionalDependencies` with
`locatePackageVersion({ parentDir: rootDir })`, which looks in the root
`node_modules/` and then searches downward **skipping dot-directories**,
so it never looks inside `node_modules/.pnpm/`. Result, reproduced by
calling the collector directly on this repo:

| Package | In desktop `.app`? | Why |
|---|---|---|
| `@openai/codex-darwin-arm64` | yes | parent `@openai/codex` is not a direct dep, so its optional children are never checked and pass through with pnpm's path |
| `opencode-darwin-arm64` | **no** | parent `opencode-ai` is a direct dep; child not found at root → "not installed" → skipped |
| `@anthropic-ai/claude-agent-sdk-darwin-arm64` | **no** | same as above — **this is pre-existing on main**; whether Claude chat tabs work in shipped builds through an SDK-internal fallback is unverified and must be checked |

The headless tarball is unaffected because `runtime-closure.mjs` stages
the closure itself.

Fix options (pick one in Phase 6):

1. `.npmrc` `public-hoist-pattern[]` for `opencode-*`,
   `@anthropic-ai/claude-agent-sdk-*`, `@openai/codex-*` so the platform
   packages appear in root `node_modules/` (smallest change; affects dev
   layout too).
2. List the platform packages as root `optionalDependencies` in
   `package.json` (explicit, but duplicates the agents' own version pins).
3. Stage runtimes with `extraResources` from the `runtime-closure.mjs`
   closure and resolve from `process.resourcesPath` (one code path for
   desktop and headless; bypasses the collector entirely).

Whichever is chosen, add a packaged-desktop smoke (Phase 6) that fails
when any bundled binary is missing — the current smokes only cover the
dev tree and the headless tarball.

### Per-arch pruning is missing

`build-mac.yml` installs with `supportedArchitectures` x64 + arm64 and
`dist:mac` builds both arches. The collector does not filter by arch, so
once the hoisting fix lands, each DMG will carry **both** arches of every
runtime (~1.3 GB of agent binaries per DMG) unless pruned. Add an
`afterPack` hook (or stage per-arch via `extraResources`) that keeps only
the target arch's `opencode-*`, `@openai/codex-*`, and
`@anthropic-ai/claude-agent-sdk-*` packages. The `mac.binaries` signing
list already names both arches' Codex binaries; keep it in sync with
whatever lands on disk.

### Hard-linked OpenCode launcher

`opencode-ai/bin/opencode.exe` and `opencode-darwin-arm64/bin/opencode`
are one inode. electron-builder's copy will materialize two files, so
either unpack only one of the two packages or point
`resolveOpenCodeExecutable` at the platform package and exclude
`opencode-ai/bin/**` from `asarUnpack`.

### Packed smoke path bug

`scripts/smoke-packed-runtimes.mjs` joins `nm, '@openai', pkgs.codexPlatform`
while `codexPlatform` already contains the `@openai/` scope, producing
`node_modules/@openai/@openai/codex-darwin-arm64/...` → `ENOENT` →
"codex: exited 1". This runs in `release.yml` and `headless-release.yml`,
so every release would fail at that step. Fixed on this branch.

### Decisions (2026-10-23)

- **App size**: the desktop app bundles Claude only. OpenCode and Codex
  are downloaded on first chat use into
  `userData/runtimes/<package>/<version>/` from the npm registry tarball,
  pinned to the versions in `package.json` and verified against the
  lockfile integrity hash. The user never runs a package manager or edits
  PATH, which is what "no manual install" means from here on. The
  headless tarball keeps bundling all three.
- **Packaging fix**: stage the per-arch closure from
  `runtime-closure.mjs` into `Contents/Resources/runtimes` (desktop) via
  an `afterPack` hook, and resolve from `process.resourcesPath` first.
  This bypasses the electron-builder collector, prunes the other arch,
  and copies the hard-linked launcher once. Until the downloader lands,
  the desktop closure stages all three runtimes so chat keeps working in
  packaged builds; it drops to Claude-only when the downloader ships.
- **Claude native gap**: confirmed as a real failure, not a latent one.
  The SDK resolves `@anthropic-ai/claude-agent-sdk-<platform>-<arch>/claude`
  itself and throws "Claude Code native binary not found" when the
  package is absent, so Claude chat tabs cannot start in the current
  desktop package.
- **Release gate**: one boolean setting, default off, that hides
  OpenCode/Codex chat entry points. Flip the default on after a signed
  build passes the packaged smoke; delete the flag one release later.

## Architecture

### Runtime model

- `ClaudeAcpRuntime` remains the SDK transport. Naming in docs/code no
  longer implies it is the generic ACP stdio path.
- `AcpStdioRuntime` (shared by OpenCode and Codex) implements the same
  `ChatRuntime` interface over a spawned subprocess speaking ACP
  JSON-RPC on stdio.
- `ChatRuntimeRegistry.register(agentKind, runtime)`; `getRuntime(sessionId)`
  resolves the session's agent kind from the slice.
- `ChatRuntimeId = 'claude' | 'opencode' | 'codex'`. `AgentKind` is
  wider (includes `pi`); `isChatRuntimeId()` gates every chat entry point
  (conversion, default tab type, session start).

### State + transport model

- Keep the `jsonClaude` slice and `jsonClaude:*` IPC surface as the
  contract. `JsonClaudeSession` carries `agentKind` and `runtimeId`.
- Chat tabs stay distinct from PTY-backed terminal tabs.

### Session lifecycle

- `start()` boots slice state; the first `send()` spawns the subprocess.
- For the stdio runtimes, Harness owns visible session state. The agent
  owns the transcript on disk; Harness uses `session/load` to rebuild
  the visible state (Phase 5), not its own transcript parser.

### Streaming behavior

- The ACP stdio runtime maps `session/update` into the same
  `jsonClaude/*` entry events with the same partial-entry + batched-delta
  pattern so the store does not churn per token.
- Unsupported features are gated via capabilities, not runtime
  conditionals in the renderer.

### Capability model

Per-runtime `default*Capabilities()` factories. Claude keeps the current
defaults. The stdio runtime starts conservative and flips flags from the
`initialize` result and `session/new` result:

| Capability | Source |
|---|---|
| `canInterrupt` | always true (`session/cancel`) |
| `canResume` | `agentCapabilities.loadSession` or `sessionCapabilities.resume` |
| `canApproveTools` | true once Phase 5 lands (ACP always sends `session/request_permission` with options) |
| `canSetPermissionMode` | `session/new` returns `modes` (Codex: read-only / workspace-write / agent / agent-full-access) |
| `canOpenAuthLogin` | `authMethods` non-empty |
| `hasSlashCommands` | first `available_commands_update` received |
| `hasCostTracking` | false unless `usage_update` carries enough to fill `SessionUsage` (see Phase 7) |
| `canRewind` | false (no ACP primitive) |

## Login (Phase 5)

Today a logged-out agent surfaces a generic error card and the user has
no way in. Required behavior:

- On `initialize`, store `authMethods` on the session (new slice field).
- Detect auth-required: JSON-RPC error `-32000` from `session/new` or
  `session/prompt` → `errorKind: 'auth-required'` and `state:
  'auth-required'` (the slice already has this state for Claude).
- The existing auth card gets a per-method action:
  - Codex `api-key`: prompt for a key, store it with `safeStorage`
    (same pattern as the GitHub PAT), pass it as `OPENAI_API_KEY` in the
    child env, then call `authenticate({ methodId: 'api-key' })`.
  - Codex `chat-gpt`: call `authenticate({ methodId: 'chat-gpt' })`; the
    agent opens the browser. If the agent requests URL elicitation,
    surface the URL in the card.
  - OpenCode `opencode-login`: the method is terminal-only. Offer "Open a
    terminal tab and run `opencode auth login`" using the bundled binary
    (spawn `opencode auth login` in a shell tab, not the PATH binary) and
    retry the session when the tab exits.
- After successful `authenticate`, retry the pending prompt
  automatically.
- Logout: Codex advertises `auth.logout`; expose it only if Settings grows
  a per-agent auth section (otherwise out of scope).

## Approvals (Phase 5)

ACP `session/request_permission` carries `toolCall` plus `options:
[{ optionId, name, kind }]` with `kind ∈ allow_once | allow_always |
reject_once | reject_always`. Map it onto the existing approval card:

- Dispatch `jsonClaude/approvalRequested` with `requestId` = JSON-RPC id,
  `toolName` = `toolCall.title ?? toolCall.kind`, `input` = `rawInput`,
  `toolUseId` = `toolCallId`, plus a new `options` field so the card can
  show the agent's own choices.
- Card actions map: "Allow once" → the `allow_once` option; "Allow this
  session" → `allow_always` if offered, else `allow_once` plus the
  existing `sessionToolApprovals` grant applied on the next identical
  request; "Deny" → `reject_once`. Respond `{ outcome: 'selected',
  optionId }`; interrupt or kill responds `{ outcome: 'cancelled' }`.
- `EDIT_TOOL_NAMES` grouping and the auto-approver are Claude-specific
  (they key on Claude tool names). Keep them inert for stdio sessions
  unless the agent's `toolCall.kind === 'edit'`; do not add renderer
  conditionals on runtime id.
- Permission mode: for Codex, map Tatsu's `permissionMode` onto the
  `mode` config option (`default` → workspace-write, `acceptEdits` →
  agent, `plan` → read-only) via `session/set_config_option` after
  `session/new`; set `canSetPermissionMode` from the `modes` returned.
  OpenCode advertises no modes; leave the flag false.

## Session continuity (Phase 5)

The plan previously assumed Claude's conversion preserved the
conversation; it does not (`persistSession: false`, no resume on either
runtime). Required behavior for OpenCode and Codex:

- Persist the ACP `sessionId` on the tab (`tab.sessionId`) once
  `session/new` returns. OpenCode's ACP id is its native `ses_*` id, so a
  terminal tab can continue it with `opencode --session <id>`; Codex's
  mapping to `codex resume <id>` must be verified against
  `~/.codex/sessions` before relying on it.
- On start with an existing `sessionId` and `loadSession: true`, call
  `session/load({ sessionId, cwd, mcpServers: [] })` instead of
  `session/new`. Replay arrives as `session/update` notifications before
  the response; feed them through the normal update path with delta
  batching so the history re-renders without per-token churn.
- If `session/load` fails (session gone), fall back to `session/new`
  and show one info card.
- Terminal → chat conversion: look up the terminal tab's session id
  (`latestSessionId` already exists per agent) and load it. Chat →
  terminal: the existing `--session` / `resume` spawn args continue it.
- Claude continuity (SDK `resume`) is a separate follow-up; out of
  scope here.

## Model selection (Phase 5)

- `session/new` returns `configOptions`; Codex exposes `model`,
  `reasoning_effort`, `mode`, `collaboration_mode`. OpenCode's option ids
  are unverified — read them from the response rather than hard-coding.
- Honor the tab's `modelOverride` by calling `session/set_config_option
  ({ configOptionId: 'model', value })` after `session/new` / `session/load`
  when the option exists; otherwise ignore and log once.
- Surface `config_option_update` and `current_mode_update` into the
  session so the model/mode chip stays accurate.

## ACP updates to support (Phase 7)

| Update | Decision |
|---|---|
| `available_commands_update` | Support: dispatch `jsonClaude/slashCommandsChanged` with the command names; send as `/name args` text in `session/prompt` (verify each agent accepts prefixed text). |
| `plan` | Support: map entries to the existing TodoWrite helper (`json-claude-todos`) — same shape (content, priority, status). |
| `usage_update` | Defer: ACP gives context `{ size, used, cost? }`, not per-model token counts, so it cannot fill `SessionUsage`. Keep `hasCostTracking: false`; revisit if the agents expose per-turn usage. |
| `session_info_update` | Support: title → tab label when the user has not renamed the tab. |
| `current_mode_update`, `config_option_update` | Support (see Model selection). |
| `fs/*`, `terminal/*` client methods | Keep advertising none. Agents fall back to their own fs/terminal. Revisit only if an agent refuses to run tools without them. |

## Non-goals

- Do not require a global CLI install, a package manager, or PATH edits.
  A first-use download of a pinned, hash-verified runtime is not an
  install prompt.
- Do not port Claude off the SDK onto the shared ACP stdio client.
- Do not rename the `jsonClaude` slice/transport surface.
- **Pi**: no chat tab in this effort. Pi has no ACP mode; its chat path is
  a future `PiRpcRuntime` over Pi's RPC mode, tracked in
  `plans/pi-integration.md` Phase 10. `isChatRuntimeId` keeps Pi out of
  every chat entry point.
- Defer a direct Codex app-server adapter.
- Do not add renderer-wide runtime conditionals; keep capability gating.
- Claude SDK `resume` for Claude chat tabs (separate follow-up).
